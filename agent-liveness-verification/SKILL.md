# Agent liveness verification

1. Read the installed `diagnose-gateway` skill and use its read-only workflow for an inspection request; obtain repair authorization before changing configuration or state. Run `openclaw status` and enumerate agent IDs with `openclaw agents list --json` rather than assuming a display name is an ID.
2. Query the target with `sessions_list` using `agentId` and a small limit, then run `openclaw channels status --probe`. Report session access separately from the target account transport status, because a connected Discord bot can coexist with an unusable agent session store. Match permission findings to the target account and its intended channel rather than treating every cross-channel Missing Access warning as its failure.
3. Inspect `openclaw cron list --json`, filtering locally to the target agent and emitting only name, enabled, schedule, payload.model, lastRunAtMs, lastRunStatus, consecutiveErrors and lastError. Distinguish historical failures from current probes, because an old task error remains until another run completes. Inspect explicit task model overrides even if the agent default has changed.
4. For a session SQLite error, run `openclaw doctor --session-sqlite inspect --session-sqlite-agent <id> --json` after confirming flags with `openclaw doctor --help`. Report integrityCheck and sqliteEntries separately from session availability; a valid SQLite file does not prove the Gateway can open sessions. Do not delete or directly edit database records to clear an application checkpoint. If repair requires stopping this Gateway, use a permitted first-class maintenance path or name the external-terminal operator step; never launch detached stop/repair/start scripts or retry a service-boundary refusal with stronger flags.
5. For an authorized model correction, inspect the existing automation, patch only its model through the available scheduler tool, then read it back. Preserve schedule, delivery, prompt and enabled state, because changing a usage-monitor label or an agent default does not fix a pinned task model.
6. After repair, repeat session lookup, channel probe and task model readback before attempting inference. Inspect the available agent-run or session-creation tool schema and allowed agent IDs before creating one isolated health-check turn under the target agent, because choosing a new session key does not itself create a session. Use the returned session handle for subsequent messaging; use `sessions_send` only with a session confirmed by creation or `sessions_list`. Set a 60-second timeout, disable channel delivery and leave the model override unset so the test exercises the configured model. Send: `This is an authorized post-repair response test. Do not call tools, send channel messages, or perform other tasks. Reply only AGENT_HEALTH_OK.` If isolated creation is denied, report that test as blocked rather than expanding permissions or substituting CLI/RPC messaging. Label any separately authorized test of an existing session as non-isolated, because it exercises existing history and bindings rather than a clean runtime.
7. Verify terminal completion, exact response, effective provider/model, elapsed time and aborted/error state from the returned receipt. If the call times out or is interrupted, inspect the existing run/session before retrying so a still-running test is not duplicated.
8. Report in concise Chinese whether sessions, transport and actual inference passed, naming the remaining blocker if any. State that a no-tools response test does not validate financial data retrieval, full scheduled reports, tool permissions or Discord outbound delivery; do not rerun a publishing report merely to prove liveness.
