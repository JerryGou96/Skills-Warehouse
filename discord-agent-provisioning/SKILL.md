# Provision a Discord specialist agent

1. Read `configure-channel` before channel changes and `browser-automation` before browser setup. Inspect `openclaw agents list --json`, `openclaw agents add --help`, and existing routing before writing, so an existing agent or bot is not duplicated. Ask whether to use an independent bot or an existing bot with a dedicated channel; preserve all other bindings and access policies.
2. Create the authorized local agent independently of pending Discord credentials with `openclaw agents add <id> --workspace <absolute-workspace> --model <provider/model> --non-interactive --json`. Use the requested exact model reference. Check that the workspace exists after creation; if initialization has not finished, inspect again rather than repeat the add command.
3. Read the seeded `AGENTS.md`, `BOOTSTRAP.md`, `SOUL.md`, `USER.md`, and `IDENTITY.md` before tailoring them. Preserve baseline rules and append the specialist role, source-verification requirements, write-action boundaries, and explicit pending integrations. Record identity in both `IDENTITY.md` and `openclaw agents set-identity --agent <id> --name <name> --theme <theme> --emoji <emoji> --json`, so file and UI identity agree. Do not install collection tools or enable recurring jobs merely because the agent was created.
4. Verify an actual bounded response through the available session-turn tool, using an isolated setup-test session and a prompt that forbids tools, external messages, and unrelated work and requests a unique literal acknowledgment. Check the returned acknowledgment, effective provider/model, terminal success, and aborted flag. Do not use a CLI or direct RPC to bypass unavailable OpenClaw messaging tools. Report local readiness separately from Discord readiness.
5. When the user asks for remote bot creation, check browser profiles and tabs before asking them to perform the entire setup. Reuse an authenticated managed-browser session when available. Open a labeled tab at `https://discord.com/developers/applications`, inspect existing applications for the intended bot, then use the visible New Application form. Re-snapshot after modal changes and submission; do not repeat creation when the outcome is uncertain.
6. If a checkbox is covered, inspect fresh page state and use its visible label or normal keyboard focus navigation, then verify its checked state before submitting. Stop at CAPTCHA, login confirmation, or two-factor authentication and request human completion in that browser session, because a populated form is not proof of application creation. Preserve the labeled tab and report the exact remaining step without claiming the bot exists.
7. After human completion, inspect the application list or application page before continuing to avoid duplicate creation. Read `references/discord-portal-setup.md` for Message Content Intent, minimal-permission invitation, desktop-app handoff, and masked credential entry. Follow the installed Discord channel documentation and `configure-channel` for account configuration and routing. Keep token values out of chat, logs, command arguments, and research notes; use an available secure setup tool or launch bare `openclaw channels add` in the operator’s interactive terminal. Follow the wizard through Discord → Modify settings (if already configured) → Add a new account → the intended account ID → masked token entry → Finished in the platform menu → routing to the intended agent → Channels updated. Verify the actual prompt rather than assuming that channel/account flags open a masked input form. Treat account names such as `agent-x` and `agentx` as distinct, and adopt the name actually saved instead of creating a duplicate. When the user says the token was entered, check wizard progress and saved metadata before requesting it again; returning to the platform menu can precede final persistence. Bind only the intended server/channel and grant only needed permissions.
8. Verify the saved account and routing, run `openclaw channels status --probe`, and use the available messaging tool for a clearly labeled delivery test to the authorized destination. Distinguish transport connection, permission audit, agent response, and successful delivery; one does not prove the others. Finish with concise Chinese status identifying what is complete and any exact human blocker, without internal skill paths or unnecessary implementation details.
