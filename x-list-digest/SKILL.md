# Configure an X List digest

1. Confirm the target account/List, destination agent and channel, and delivery cadence before enabling a recurring job. Resolve Pacific-time schedules with `America/Los_Angeles`, not a fixed UTC offset, so daylight-saving changes follow the user’s intent.
2. Read browser-automation before using browser controls. Inspect existing tools with `command -v bird`, `command -v opencli`, and, when considering Bird, `npm view @steipete/bird version deprecated repository.url --json`; choose from current maintenance and live test results rather than assuming an older tutorial’s bundled tool still works. Do not purchase services or install plugins without the required authorization.
3. If opencli is installed, inspect `opencli twitter lists --help` and `opencli twitter list-tweets --help`, then test `opencli twitter lists --limit 50 --trace off`. Report any connection failure accurately and test the already authenticated OpenClaw browser as an alternative; a CLI bridge failure does not establish that X itself is inaccessible.
4. Inspect browser profiles and tabs, reuse the authenticated X tab, and navigate to `https://x.com/<loggedInHandle>/lists`. Find the exact list title and owner, open its visible link, and record `https://x.com/i/lists/<numericId>` as the durable source. Do not treat `/i/lists` as a reliable substitute for the account-specific list page or hard-code transient tab IDs.
5. Verify an actual read-only sample before scheduling. Extract bounded rendered `article` text, author, `time[datetime]`, and the status URL from the time element’s enclosing anchor. Expand Show more or visit the selected post before treating truncated content as complete. Deduplicate translated/original renderings and status IDs; distinguish quoted-post authors and times from the enclosing post. Never click engagement or membership controls.
6. Write the agent’s monitoring runbook with the canonical list URL, verified access method, source timezone, output destination, and bounded collection limits. Specify a rolling 24-hour window where requested, post-ID deduplication, topic grouping, source links, and explicit fact/opinion/rumor attribution. Require observed coverage and failed/truncated items to be reported; list membership counts and a sample read do not prove exhaustive collection. Do not stop on one old repost because list ordering and original timestamps can differ.
7. Inspect existing automations for that agent before adding one. Use the automation tool when available; otherwise inspect `openclaw cron add --help` and use an idempotent `--declaration-key`, explicit `--agent`, `--cron`, `--tz`, `--model`, and Discord `--account`/`--to`. Reference the runbook and required browser-automation skill in the payload. Have the scheduler deliver final text once rather than also sending it inside the job. Keep credentials out of runbooks, reports and prompts.
8. Require access failures to produce a concise blocker notice rather than a fabricated digest or silent no-news result. Use NO_REPLY only after successful inspection establishes no useful new content in the observed sample. Preserve undelivered reports for retry and distinguish generated content from confirmed delivery.
9. Read back the saved schedule and next-run time in the user’s timezone. Report collection sample verification separately from full scheduled-run verification; do not claim the latter before a completed run and delivery receipt. State that the host must remain awake, Gateway available and browser session authenticated. Prefer concise Chinese, Discord-friendly bullets with original post links and no tables for this user.
10. When asked whether webpage access failed, inspect the automation detail and latest run through the automation tool, or `openclaw cron get <job-id>` and `openclaw cron runs <job-id> --limit 2` when that tool is unavailable. Read the generated Markdown report from the configured reports directory, because scheduler success and delivery do not prove the requested collection window was covered. Compare the requested window with the main timeline’s oldest observed post, unique-post count, and reached screen/time limits; report old repost timestamps separately rather than treating them as continuous coverage.
11. Check current browser tabs, then reuse or open the canonical List URL and snapshot it to verify the account, List title, and visible posts. Treat an empty tab list as no open pages, not lost authentication. Separate current X access, historical collection limits, and linked-source verification failures in the diagnosis; an official-source HTTP 403 does not establish an X access failure. Report successful delivery and incomplete coverage together when both occurred, and do not label a partial sample a complete daily digest.
