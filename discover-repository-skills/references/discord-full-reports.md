# Capture complete Discord commentary reports

1. Complete `discord-desktop-verification.md` first and retain the exact guild/channel IDs, because connection success alone does not establish source access. Use the isolated compatible CLI without changing the global runtime.
2. Inspect the installed adapter with `rg -n "slice|substring|Message:" "$RUNTIME/node_modules/@jackwener/opencli/clis/discord-app/utils.js"`. In the tested adapter, preserve a backup and replace only `Message: messageText.slice(0, 300),` with `Message: messageText,`; keep channel guards unchanged. Re-read a known long message and verify its closing text and length exceed 300 characters, because increasing `--count` does not remove per-message clipping. Record the small patch in the runtime documentation so reinstall verification can restore it.
3. Save a bounded `discord-app read --count 100 --channel CHANNEL_ID -f json` result, but inspect earliest timestamp and headings rather than assume 100 rows were loaded. Discord virtualizes message history; the option limits rendered rows rather than paginating history.
4. For full-text and author metadata missing from the adapter, attach a read-only helper to the same desktop CDP endpoint. Fetch `/json`, select the page whose URL matches the exact `discord.com/channels/GUILD_ID/CHANNEL_ID`, connect to its `webSocketDebuggerUrl` using the isolated runtime’s `ws`, and issue `Runtime.evaluate` with `returnByValue:true`. Abort on a wrong page, evaluation exception or timeout; do not extract tokens, cookies or private application stores.
5. Extract rendered `li[id^="chat-messages-"]` elements. Preserve `[id^="message-content-"]` innerText without whitespace flattening or clipping, `time[datetime]`, message ID, channel ID, visible edit metadata and attachment links. For continuation messages, follow the article’s `aria-labelledby` username reference rather than interpreting an em dash as a different author. When a numeric author ID is needed, inspect only the rendered article’s `__reactFiber*` ancestor `memoizedProps.message.author` fields (`id`, `username`, `globalName`), bounded to 20 ancestors; verify against the visible profile before persisting identity. Do not dump the entire React tree or unrelated user data.
6. Save each batch by message ID before scrolling. Locate the actual message-list scroll container by its containment and scroll geometry; the tested class was `[class*="scroller__36d07"]`, but verify it instead of assuming stability. Scroll that container to the top, allow roughly 900 ms for history loading, then extract the next batch. Merge by message ID, preserving changed versions by content hash. Stop once the prior report start is covered, after a bounded page budget, or on repeated no-progress; report gaps rather than repeatedly scrolling indefinitely.
7. Compute dates and output paths from the requested report date and timezone. Parameterize any helper with report date, comparison date, guild/channel and output directory; never schedule a prototype containing literal dates or fixed output filenames. Keep this desktop capture serialized because navigation and scrolling affect the shared app.
8. Assemble messages from the verified author in chronological order. Recognize optional numbering and the five headings Macro Regime & Setup, Top Signals, Earnings Digest, Extra Alpha Playbook and Levels; include continuation messages until the closing passage. Separate subsequent intraday headlines from the morning report. Require all five sections plus a meaningful ending, not just the Levels heading. Check attachments separately and disclose unreadable content.
9. Save original messages, source links, UTC timestamps, local report interval, author ID, section mapping, completeness and hash before writing analysis. Capture the previous complete trading-day report directly when available; name the comparison dates and label a pasted baseline as user-supplied if direct evidence is unavailable. Verify section counts and inspect long-message endings as the smallest completeness test.
10. Summarize in Chinese in this order: remarks summary; one-sentence stance; changes from the prior report; key conditions/levels; completed versus intended actions; missing information. Attribute financial claims to the author unless independently verified. Distinguish long-term thesis from short-term trading posture, intended adds from self-reported fills, add zones from stops, and hypothetical downside levels from unconditional buys. Treat omitted tickers as not updated, not closed. Preserve ambiguous ticker spelling with a warning.
11. Report manual capture and scheduling separately. A complete manual report does not prove an unattended run or delivery receipt; retain disabled scheduling until the dynamic-date runner, source capture, duplicate suppression and delivery are tested.
