# Schedule a verified desktop report workflow

1. Read the existing report skill and runtime before creating another entry point; preserve one production workflow and route older entries to it, because competing prompts can invoke obsolete prototypes. Edit user-owned skill sources directly only when authorized.
2. Compute runtime dates with the requested IANA timezone instead of literal dates. Use Intl.DateTimeFormat with timeZone in Node or datetime.now(ZoneInfo(TZ)).date().isoformat() in Python. Test around UTC midnight and daylight-saving boundaries, because report dates differ from host or UTC dates.
3. Check the desktop connection, navigate to the exact channel, and move the message list to its latest messages before paging upward; a prior investigation may have left the shared app on old history. Serialize captures with an exclusive lock, bounded scrolling, a wall-clock timeout and evaluation-error handling. Confirm no active capture before clearing abandoned locks.
4. Save hash-versioned raw snapshots, a latest-capture manifest and a separately assembled report. Preserve old manual artifacts. Assemble by verified author and local date, require configured sections and a genuine closing passage, and exclude subsequent intraday news. Disclose attachment gaps and uncertain endings rather than accepting heading counts alone.
5. Separate capture, assembly and delivery state into testable helpers. Run node --check PATH/capture.mjs, execute the real capture, and run python3 PATH/assemble.py; inspect message counts, section counts, long-message endings and the previous complete baseline. Exercise incomplete-report and missing-baseline cases before scheduling.
6. Implement a per-date delivery claim using exclusive creation such as Path.open("x"). Save pending before sending, commit delivered only with a platform message ID, and reject a second claim. Test claim, duplicate rejection and commit in a temporary directory. Reconcile pending or unknown delivery against destination history before retrying, because transport failure can occur after a successful send.
7. Read back an already-posted manual report and record its real message IDs before same-day acceptance tests; do not invent receipts or resend merely to populate state. Keep destination access separate from the desktop source reader.
8. Inspect existing scheduler jobs and preserve their IDs when updating. Bind the production skill by absolute path, set working directory and IANA timezone explicitly, and constrain delivery to the authorized destination. With explicit message-tool delivery, set runner fallback delivery to none and finish silent runs with NO_REPLY, because two delivery paths duplicate reports. Route configuration changes through the responsible agent when workspace ownership requires it.
9. Configure a bounded check window and separate final check using the agreed schedule. For weekday 06:00–07:00, use cron expressions */5 6 * * 1-5 and 0 7 * * 1-5 in the requested timezone. Publish once when complete, save incomplete checks quietly, and issue one labeled incomplete/no-report notice at cutoff. Distinguish access failure from no new content; never substitute yesterday for today.
10. Run an isolated scheduler dry-run with real desktop capture and assembly, forbidding claim, send, commit and delivery-state changes. Require terminal completion, saved artifacts and unchanged delivery state; accepted or running is not a passing test. Enable production jobs only after passing, then read back enabled flags, bound prompts and next-run timestamps converted to the user timezone.
11. Deliver a Markdown operations document containing the skill entry point, schedule, output paths, prerequisites, completeness checks, duplicate handling and failure behavior. Update activation status after verification and attach the final file through the messaging tool. State what was tested, the next run time, and that the host and authenticated desktop must remain available; enabled scheduling is not a guarantee of future delivery.
